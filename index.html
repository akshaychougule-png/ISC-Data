Integrated Supply Chain

How Cognite's Integrated Supply Chain offering models hierarchies, organizes data into governed domains, and grounds AI agents in a single knowledge graph spanning the supply chain and the plant floor.

Overview

Integrated Supply Chain (ISC) extends the Cognite Data Fusion Core Data Model (CDM) with a purpose-built data model for industrial supply chains — procurement, inventory, logistics, demand, planning, and plant-floor operations — modeled as one connected knowledge graph rather than a collection of disconnected systems.

Three layers make up the offering:

Hierarchies

Dedicated materialized trees

Four BTP-owned hierarchy trees (BusinessUnits, GeoLocations, Products, StorageLocations) run on their own containers, independent of cdf_cdm, with paths computed automatically.

Data model

10 governed domains

Supply-chain entities are split across ten schema spaces, connected where needed by typed edges that carry their own business facts.

Agents

Atlas AI, grounded

Three published agents answer plain-language questions over the graph, escalating from fast single-hop reads to specialist multi-hop tools only when needed.

Scope note FunctionalAsset — the generalized ISA-95 physical-asset view — is deliberately excluded from the BTP hierarchy model. It stays on CDM's native CogniteAsset path tree and links into ISC domains via ordinary direct relations, keeping operational asset structure isolated from commercial/organizational hierarchies.

Hierarchies

Why Integrated Supply Chain replaces one shared asset tree with four dedicated, materialized hierarchy trees.

Why dedicated trees, not one shared CDM container

Standard CDF CDM models physical plant/manufacturing equipment on a single, unified asset hierarchy container (cdf_cdm / CogniteAsset). A supply chain, however, has several distinct hierarchical concepts — organizational, geographic, commercial, and logistics — that don't belong in one shared container.

Single CDM containerISC dedicated containers
Every instance shares one asset treeEach hierarchy owns its own container
An update recomputes paths for the affected subtreeAn update computes paths only within that tree
One overcrowded container risks a performance bottleneck at scaleOther trees stay untouched — no shared bottleneck

Source: adr/0001-custom-hierarchy-on-btp-containers.md

Path synchronization runs asynchronously whenever an instance changes. Two safeguards keep it from running away:

  • Path-write echo loop — skips reprocessing a change that was itself caused by the sync's own prior write, preventing infinite recomputation loops (implemented as path_echo_skip in path_sync_cursor.py).
  • Per-view lock — blocks concurrent writers on the same view, so locking is scoped per hierarchy, never global.

Four separate WorkflowTriggers — one per tree (business_hierarchy, geo_location, product_hierarchy, warehouse) — feed the same shared function and workflow, so isolation between trees comes from per-view locking, not from running separate code per tree.

Strongly typed hierarchies

Legacy trees relied on a plain text discriminator field (e.g. hierarchyType) checked only in application code. Strongly typed hierarchies replace this with formal schema types, enforced directly in the data model.

Shared hierarchy container
parent, root, path, scalars
→
Interface view
path-sync target
→
Concrete per-level views
e.g. City, ProductFamily

A DeclaredTypes catalog, combined with a filter.equals filter on the catalog-instance externalId, partitions instances from the shared container deterministically into exactly one concrete view. AI agents default to reasoning over concrete per-level views, touching the interface view only when explicitly required.

Data model split CDF caps a single data model at 100 views. Interface views now register on per-domain models (OrganizationalFoundation for BusinessUnits/GeoLocations/Products, MaterialManagement for StorageLocations), while concrete per-level views live on isc_typed_model. The original single integrated_supply_chain base model is legacy and no longer deployed (adr/0013-per-domain-datamodels.md).

Data model & domains

How ISC splits the knowledge graph into governed schema spaces, and how typed edges connect them.

Ten schema-space domains

Procurement, inventory, logistics, and plant-floor operations inside one unorganized container makes access control impossible and maintenance fragile. Common mistake sp_isa_manufacturing is sometimes mis-typed as ssp_manufacturing. The ssp_ prefix belongs only to sp_ssp_supply_chain, a legacy, no-longer-deployed monolith model — unrelated to the current manufacturing domain.

Nodes vs. typed edges

A node represents a standalone business entity (MaterialMaster, Supplier, CustomerOrder) with scalar properties that exist independently. A typed edge models a relationship that carries facts of its own — a reserved quantity, a unit cost, a transit date. The deciding test for using an edge is whether the relationship carries its own facts, not simply whether it's many-to-many; a plain 1:N structural link with no extra properties stays a direct relation.

Source: adr/0002-edge-native-many-to-many-data-model.md

Common mistakes The commercial edge is SupplierSuppliesMaterial, not the shorter SuppliesMaterial. Its minimum-order-quantity field is minQuantity (not minimumOrderQuantity), its contract reference is contractRef (not contractReference), and its OTIF field is otifScore (not onTimeInFullRate).
